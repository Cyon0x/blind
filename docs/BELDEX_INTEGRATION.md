# Beldex integration

What Blind actually calls, what it verified, and what Beldex cannot do.

Everything below was checked against primary sources — the official `@bdxi`
packages on npm, Beldex's own WASM wallet core, and a live mainnet node — rather
than assumed. Where a fact could only be established by running something, the
command that establishes it is included.

## Supported network and assets

- **Network**: `mainnet` by default; `testnet` and `devnet` are supported by the
  address codec and the escrow path. `BDX_NETWORK` selects it and everything else
  follows.
- **Asset**: BDX only. Blind's payment forms do not offer a second asset, because
  nothing else can actually be moved by this integration. There are no
  USD-denominated payments, so there is no implied conversion rate and no
  volatility claim anywhere in the UI.

## Dependencies

| Package | Version | Role |
| --- | --- | --- |
| `@bdxi/web3js` | 1.0.1 | The browser wallet SDK (`connect`, `getBalance`, `sendTransactionSafe`, `connectWithProof`, `resolveBns`). User-authorised sends only. |
| `@bdxi/beldex-nettype` | 1.0.0 | The prefix table Blind encodes addresses against. |
| `@bdxi/beldex-app-bridge` | 3.0.2 | Dev dependency. Beldex's own WASM wallet core, used as an independent oracle in the address tests. |
| `@noble/curves`, `@noble/hashes` | 2.x | ed25519 arithmetic and keccak-256 for address checksums and `SigV1` signature verification. |

## Address encoding

```
address = monero_base58( varint(prefix) ++ spend_pub(32) ++ view_pub(32) [++ payment_id(8)] ++ checksum )
checksum = keccak256(payload)[0:4]
```

Two details matter and are easy to get wrong:

- **The prefix is a LEB128 varint, not a fixed byte.** Mainnet `standard` is 209,
  which needs two bytes, giving a **97-character** address. Testnet is 53 — one
  byte — giving **95 characters**. A verifier that assumes one byte rejects every
  mainnet address.
- **Base58 is Monero's variant**: 8-byte blocks encode to 11 characters, and the
  final block's character count (2,3,5,6,7,9,10) maps to 1–8 bytes.

Prefix tables: mainnet `{standard: 209, integrated: 19, subaddress: 42}`, testnet
`{53, 54, 63}`, devnet `{24, 25, 36}`.

**Verified** in `tests/beldex-address.test.ts`: address bytes are reproduced
byte-for-byte against fixtures generated by Beldex's own WASM wallet core
(mainnet `bxbz7CtrYjjj…ZERf8`, testnet `9t4NTtku1BAX…fMbfR`).

## Wallet connection

Blind uses two independent wallet paths, and says which is which in the UI:

1. **The Beldex Wallet browser extension**, through `@bdxi/web3js`. The SDK is
   imported lazily on the client so no server render touches `window`. The user
   approves a connection in the wallet; reads (`getBalance`) happen only after
   that, and a send needs fresh approval inside the wallet.
2. **A pasted address**, recorded as `source: 'pasted'` and never as verified.
   `ownership_proven_at` stays null until the address is proved.

Address ownership can be **proved** with a wallet signature
(`connectWithProof` → `POST /api/auth/wallet/verify`), which also signs a user in.
There is no embedded/Beldex-provisioned wallet: Blind has no way to create a
web-based wallet that holds a spend key without becoming a custodian of every
user's funds, which the design rejects. See *Wallet provisioning* below.

## Transaction authorization and submission

Blind never signs anything on a user's behalf.

- **User sends** (funding a payment, paying a request): the browser asks the
  wallet extension to sign, using `sendTransactionSafe({ to, amount,
  idempotencyKey })`. The idempotency key is the payment reference, so a retry
  cannot pay twice. A send that does not return a definite result is reported to
  the user as **unknown outcome** and never resent automatically.
- **Escrow sends** (payouts and refunds) are signed by `beldex-wallet-rpc`, which
  the app reaches over HTTP. Blind never has the escrow's key material in-process;
  it calls `transfer`.

## Transaction verification

Two independent sources, and the app reports which answered:

- **The escrow wallet** (`get_transfers`, `get_bulk_payments`,
  `get_transfer_by_txid`) — it knows what it received and what it sent.
- **The daemon** (`get_transactions`, `get_info`,
  `get_block_header_by_height`) — it knows whether the chain in the chain.

`get_transactions` does not return a confirmation count, so Blind derives it as
`height − block_height + 1` and re-reads the block header so a reorg shows up as a
changed block hash. The response's `untrusted` flag is recorded: a receipt issued
from a bootstrap node says so.

**Verified live** (`npm run bdx:doctor` against
`http://publicnode1.rpcnode.stream:29095/json_rpc` on 2026-10-09):

```
  ok daemon: get_info — height 5822269, OK
  ok daemon: get_height — height 5822269
  ok daemon: get_block_header_by_height (reorg checks) — hash 6ea477622339f61c…
  ok daemon: get_fee_estimate — 6666 atomic per byte
```

Note that this public node answers **plain HTTP only**; HTTPS fails its TLS
handshake. Point `BDX_DAEMON_URL` at your own node for production, and treat any
answer from a bootstrap node as corroboration rather than proof.

## Escrow (beldex-wallet-rpc)

The escrow service is deliberately *not* part of the web app:

- one **fresh subaddress per payment** (`create_address`, labelled
  `blind:pay:<reference>`), so deposits cannot be confused or merged;
- a **unique integrated-address payment id per payment**
  (`make_integrated_address`), which is what `get_bulk_payments` matches on;
- payouts only via `transfer`, only to the destination recorded by the claim, and
  only after the hot-cap check in `escrowHealth()`.

The reference for txids is `get_transfer_by_txid`; reconciliation after an
ambiguous send (`reconcileOutgoing`) searches `get_transfers` for a matching
amount and destination rather than sending a second transfer.

**Not verified on this machine.** `beldex-wallet-rpc` ships for linux and
macOS-arm only — there is no `darwin-x86_64` build, and Docker is not installed
here — so every escrow operation in this repository is implemented but has not
been exercised against a live wallet. Blind therefore reports
`escrow_unavailable`, creates no claim that appears funded, and the doctor prints
`skip` for each wallet check. This is a hosting blocker, not a code path that has
been faked.

## Wallet provisioning

Blind does **not** provision wallets.

An embedded Beldex wallet would mean Blind (or a provider) generating and holding
spend keys for users. Beldex's app-bridge can do key operations in WASM, but
custody of user funds by the payment app is exactly what Blind's design refuses,
and social login is not a recovery mechanism for a spending key. Users bring a
wallet — the extension, or any address they control — and Blind never sees a seed
phrase, view key or spend key. The UI states this and offers no field for one.

**Remaining integration question**: if Beldex publishes an audited
non-custodial in-browser account model (e.g. a documented key-derivation scheme
the user can back up outside the app), Blind could add it behind the same wallet
interface. Until then, "embedded wallet" is reported as not implemented rather
than approximated.

## Unsupported operations

- No EVM compatibility, and none assumed.
- No on-chain scripting or conditional payments: Beldex transactions have no
  scripts, so a claimable link cannot be trustless. See
  [PRIVACY_THREAT_MODEL.md](PRIVACY_THREAT_MODEL.md) for the custody this implies.
- No atomic swaps, no second asset, no fiat rails, no BNS-based payment
  resolution (the SDK exposes `resolveBns`, and Blind surfaces it as a wallet
  capability, but no payment path depends on it).
- No custom cryptography. Blind implements no mixer, no claim pool, and no
  zero-knowledge proof, and claims none.
